# 生产报数核对卡片模板同步指令

> 对应工作台版本：V1.18；正式发布：2026-10-06-v1.18

创建日期：2026-09-22
适用对象：小文CEO、生产统计工作台、飞书群生产报数核对卡片生成程序。

## V1.18 历史缺项补核模板（优先适用）

已有生产记录的历史补核先绑定员工和原生产日期，读取 GitHub 当前六项记录。已有数量保持原值，只补此次明确填写的待核实项；未填写的缺项保留待核实，不能自动填0或发可确认的全零卡。

补齐后完整核对卡逐项标明“原有记录”与“本次补核”，合计包括保留的原有数量。提示为：“请核对原生产日期的完整六项数量。已有记录保留，只补本次明确填写的缺项，不新增重复产量。无误回复准确；有错回复错误，旧卡停用后重新核对。”

下方六项缺报按0的通用模板只用于经过实际报数校验的正常批次；不得套用到历史缺项补核、状态核实、无数量消息或已撤销卡。多张有效卡并存不得猜最近一张。

## 年度台账与实时网站

核对卡按明确生产日期选择台账：2027-01-01至2027-12-31使用独立2027全年台账；历史补核保留原年度，禁止按今天或发送日期归账。最新正式规则同时适用于2026和2027，2026员工数量和消息凭证不复制到2027。

手机和电脑共用年度切换入口：[2027年实时生产统计工作台](https://tengtiao-calc-d8gpq679da44f9bc2-1497888928.tcloudbaseapp.com/production-dashboard/index.html?year=2027)，按年度发布快照每30秒核查更新。

## 目标

小文程序里的“生产报数核对卡片”必须和《00-生产统计工作台规则.md》的最新口径一致。员工报数后，应快速返回一条简洁核对消息；收到本人回复“准确”后，才正式上传 GitHub 台账。缺失日期核实卡只显示“当天未上班、已经报过、需要补报”三个选项，三种选项都要经过核对并同步 GitHub；多日按日期逐张推进，上一日完成 GitHub 回读和飞书成功回执后才发送下一日。

自动缺失提醒和手动补报必须调用同一状态机：当天未上班、已经报过、需要补报均生成当前日期的一张核对批次；前三者只有在 GitHub 提交、远程回读和飞书成功回执都完成后，才允许推进下一日期。自动提醒在生产日下一个自然日中午12:00触发，周六、周日和节假日照常运行；手动补报始终保留，但不得与同日自动卡重复发送。

## 历史日期待核实提醒模板

A、B 固定班次和 C 长期上班员工出现应上班但无记录时，飞书先发送对应日期的核实卡；员工回复“补报”后，再发送已绑定日期的可复制补报模板。若老板已明确确认某个日期需要补报，可直接发送该日期的补报模板，不再要求员工重复回复“补报”。D 只有明确某日应上班时才使用同一提醒卡。已查到记录、已报待查、员工说明未上班或系统暂时无法检查时不发补报提醒。每个日期单独发送一张提醒卡，不得让员工合并不同日期的数量。

检查时间：A、B、C统一在对应生产日的下一个自然日中午12:00检查，周六、周日和节假日照常执行；D没有明确上班日期时不自动检查。自动提醒与手动补报共用同一核对、GitHub提交、远程回读和飞书回执链路。

```text
【生产报数待核实】

员工：B｜梅芳
待核实生产日期：2026-09-20

当天确实上班但统计中没有记录。请先回复：补报

收到“补报”后，系统会发送已绑定员工和生产日期的补报模板。收到模板后，请复制整段内容，**只把六个 `___` 替换成数字**，不要修改或删除员工、日期、工序和产品名称；没有生产的项目填写 `0`，六项必须全部保留。

补报
B=梅芳
生产日期：2026-09-20
棉堆堆袜：___
冰冰袜：___
小腿袜：___
过膝袜：___
女船袜：___
男船袜：___

没有生产的项目填写0，六项必须完整填写。填写完成后，将整段模板发送回来，系统再生成核对卡。
如果当天未上班，请回复：未上班：2026-09-20
如果已经报过，请回复：已报待查：2026-09-20
系统按生产日期入账，回复“准确”后才上传。
```

不同生产日期必须分别发送；不能填写“2026-09-20、2026-09-21”并合并数量。C、D 时间不固定，不因空白日期自动发送此提醒。员工不能单独发送没有对应核实卡的“补报”，否则系统无法确定日期。

- 身份、数量都正确，请回复：**准确**
- 有错，请回复：**错误**，并直接重报完整、正确的六项生产数量；缺项明确填写0

## 字段显示规则

- 身份必须显示为：`身份：A = 徐超超，请核实`、`身份：B = 梅芳，请核实`、`身份：C = 李鸿玉，请核实` 或 `身份：D = 张小翠，请核实`。
- 员工明确填写 `0`，或没有填写数量的产品，显示为：`0双（数量为0，请核实）`。
- 员工明确写了“本次未上机”的产品，可以显示为：`0双（数量为0，请核实，本次未上机）`。
- 员工回复“准确”后，核实项按 0 双进入上传候选；如果实际忘记上报，回复“**错误**”并重报完整、正确的六项生产数量，缺项明确填写0，系统重新生成完整核对卡。
- 卡片正文使用 `lark_md`，提示员工回复的“准确”和“错误”必须加粗显示，分别使用 `**准确**`、`**错误**`。
- 合计按当前六项清单计算，核实项按 0 双计入。
- C=李鸿玉、D=张小翠的工序为烤边；A、B的工序为下机。C、D均按白天为主、可能加班/时间不固定处理。

## 禁止继续输出的旧卡片内容

生产报数核对卡片不得再向群里显示以下内部字段或旧话术：

- `生产报数核对 · 91f00...` 这类核对卡编号标题；
- `原报数消息：om_...`；
- `当前待核对，尚未上传。` 这类长说明可以保留含义，但不要展示内部状态编号；
- `如暂不上传，请回复“暂不上传”`；
- `不使用按钮`；
- 重复两遍“尚未上传，请回复确认”的说明；
- `员工代号：C（李鸿玉）` 这种旧格式，应改为 `身份：C = 李鸿玉，请核实`；
- 让员工回复复杂口令，例如 `C确认`、`修改数量` 加固定格式等。

## 快速回复要求

- 收到员工报数后，先快速生成核对清单并发到群里，不要等待 GitHub 写入。
- 核对清单阶段不得写正式台账。
- 收到“准确”后，再执行 GitHub 上传。
- 上传成功并完成远程回读后再回复“已上传台账”，并在详细生产数据与三项提交凭证后追加 GitHub 回执：`已更新：<本次实际上传的对应年份台账文件名>`、`同步验收：全部一致`、运行时 `VERSION.json` 的实际 `生产统计工作台版本`、真实的 `远程 commit`。版本号只放在成功 GitHub 回执中，核对卡继续不展示版本号或内部 ID。
- 成功回执使用蓝色标题、白色正文的飞书 interactive 卡片，保留原有正文与提交凭证；员工字段按已核实映射同时显示代号与姓名，例如“员工：B（梅芳）”。
- GitHub 回执必须由本次实际上传及远程回读结果生成；上传失败、commit 缺失或回读不一致时不得显示成功回执。
- 如果 AI 服务过载或模型失败，应返回简短失败提示，并保留待核对状态，不得丢失原始报数。

## 跨月、跨年入账与失败回执

- 上传目标按生产日期选择：2026 年 10—12 月写入 2026 下半年主账，2027-01-01 至 2027-12-31 写入 `2027全年下机白胚半成品统计.md`；不得按上传时间或确认时间选择台账。
- 月度个人累计只计算当月，全年累计只计算目标台账的年度范围。写入前必须执行动态月份/年度 guard；guard 失败时不得生成“已上传成功”回执。
- GitHub 台账写入失败时，保存真实失败原因；例如缺少月份区块时，员工状态显示“已确认，上传因台账月份结构失败”，不得提示员工重新报数或重新确认。每30秒扫描恢复队列，同一确认自动上传尝试累计最多3次，达到上限后转管理员处理；修复后可使用原报数和原确认恢复该批次。
- GitHub 已验证后若飞书成功回执失败，只重试成功回执，最多自动重试3次；连续失败转人工补发，不再次上传、不重复计量。
- 核对卡已发送而员工未确认时，保留原提醒规则：首次发送后5分钟补发一次，再等待30分钟最多补发第二次；员工确认后停止提醒。此处最多2次提醒与成功回执的3次重试分别计数。
