# 袜子生产统计工作台规则

> 工作台版本：V1.18
> 正式发布：2026-10-06-v1.18（GitHub、飞书、OpenClaw、手机与电脑网站统一验收）
> V1.17 口径修复：选择“当天未上班”或“已经报过”只保留出勤核实状态，不再把六项 0 双写入生产明细、生产天数、产量或个人/月度/年度累计；2026 与 2027 台账统一展示有效生产和状态核实。
> V1.16 意图分流修复：历史统计/产能分析请求进入只读查询流程，不得生成生产补报核对清单；只有包含明确员工、生产日期、工序及六项数量的报数消息才进入报数核对流程。
> V1.15 同步要求：正常报数流程保持不变；无有效记录时先核实原因，不直接要求补报。A/B/C统一在生产日次日中午12:00检查，周六、周日和节假日照常执行；D只有明确当天上班才检查。无误回复“**准确**”；有错回复“**错误**”并重报完整六项。补报先回复“补报”，系统再发送已绑定员工和生产日期的模板；员工复制整段模板，只修改六个数量数字，其余字段不改。补报按明确生产日期单独入账，写入前检查员工+生产日期重复记录。上传失败保留真实原因，同一确认自动上传尝试累计最多3次；GitHub 已验证后，飞书成功回执失败最多自动重试3次，连续失败转人工补发，不重复上传。
> 版本用途：记录生产统计规则、状态判断和同步边界的正式版本。规则变更必须递增版本号，并与 GitHub commit 一起记录。

## V1.18 当前正式规则（2026-10-06，优先于旧版本同类说明）

- 正常报数、自动补报、手动补报和历史缺项补核统一通过实际运行的核对、确认、GitHub 写入、远程回读和飞书回执链路；模型只能提取草稿，不能自行上传或编造核对卡。
- 历史缺项补核必须绑定真实发送人、唯一生产日期和原台账。先读取 GitHub 当前记录，保留已确认数量，只补原记录标为待核实的项目。生成完整六项合并清单后再确认；不得把补核消息当成当天新增产能，不得重复累计。
- 带日期的缺项消息未完成合并时，不能直接生成可确认卡或上传。无数量、按钮文字、只报零的缺项消息不能生成六项全零产能；原消息有非零数量时更不能生成全零核对卡。明确完整报零和出勤状态仍分别处理。
- 核对卡发出、补发和确认前重新验证六项数量、合计及生产日期；历史补核卡内容与合并结果不一致立即停用。写入前原台账变化时暂停，保留原数据，重新核对。
- 同一员工同一日期的重复补核复用原任务；不同版本冲突暂停。存在多张有效待确认卡时，不能用无指向的“准确”猜测最近一张。撤销、错误或删除的卡不能继续确认、补发或上传；删除旧消息内容后，仅保留无内容的防重放指纹。
- 网络或远程 SHA 冲突按同一确认批次退避恢复，不新增任务、不要求员工反复报数；固定业务校验失败保持暂停。GitHub 已验证后只补发缺失成功回执，不能再次写入。
- 手机和电脑使用同一个发布网站与正式 GitHub 台账。每30秒检查发布标识；显示规则版本、数据快照和更新检查状态，页面刷新时间不能代替数据更新时间。发布后必须线上回读匹配，失败不能显示正常或发布成功。
- 手机入口：https://tengtiao-calc-d8gpq679da44f9bc2-1497888928.tcloudbaseapp.com/production-dashboard/index.html
- 2027全年入口：https://tengtiao-calc-d8gpq679da44f9bc2-1497888928.tcloudbaseapp.com/production-dashboard/index.html?year=2027；手机和电脑可切换年度，2027支持1—12月、单人/全部员工查询与实时发布。报数、补报和历史补核按明确生产日期进入对应年度台账，2026数量不迁入2027；页面切换不改变入账年度。

## V1.13 简化核实、补报与提醒规则

- A、B 按固定班次检查历史空档；C 为长期上班员工，统一在生产日次日中午12:00检查，周末和节假日照常执行；不按实际结束时间计算。
- D 工作时间看安排，只有明确当天上班才检查；如果已确认某段时间只上班一天，其余日期不逐日提醒。
- 已查到有效记录、已报待查、员工已说明未上班或系统暂时无法检查时，均不发送补报提醒；只有确认应上班但没有有效记录时才发送核实卡。
- 员工总览每人只显示一行，多个日期放在同一行；详细记录按生产日期展开，避免同一员工重复显示。
- 补报必须填写明确的生产日期。系统按生产日期写入对应月份和年度台账，不按消息发送日期写入。
- 每条补报只允许一个生产日期。员工需要补报多个日期时，必须分别发送多条完整报数，不能合并日期或合并数量。
- 补报必须填写棉堆堆袜、冰冰袜、小腿袜、过膝袜、女船袜、男船袜六项；没有生产的项目填写 0。
- 员工发现确实上班但漏报时，先在对应日期核实卡下回复“补报”；系统再发送已绑定员工和生产日期的补报模板。当天未上班时回复“未上班：YYYY-MM-DD”；已经报过但未显示时回复“已报待查：YYYY-MM-DD”。
- 补报模板必须明确提示：员工复制整段模板，只把六个 `___` 替换为数字；员工姓名、代号、生产日期、工序和产品名称不得修改或删除；没有生产的项目填写 `0`；六项必须全部保留。系统收到完整模板后才生成核对卡。若老板已明确确认某个日期需要补报，可直接发送该日期的补报模板，不再要求员工重复回复“补报”。
- 补报先生成独立核对卡，员工回复“准确”后才进入正式上传；有错回复“错误”，并重新填写同一生产日期的完整六项数量。
- 写入前按员工和生产日期做重复检查。已有有效记录的日期禁止重复补报，需走更正流程；不得重复上传或重复计量。
- 待核实、补报待确认和未上班均不计入累计；只有 GitHub 写入、远程回读和成功回执完成后才计入正式累计。

## 适用范围

本规则适用于袜子生产统计工作台的群内报数、老板私聊同步、核对、查询和 GitHub 台账入账。

工作台的唯一正式数据来源是经过核对并上传成功的 GitHub 台账；群聊历史回复、模型记忆、计划数量和测试数据都不是正式数据来源。

## V1.16 统计查询与生产报数意图分流（强制）

先判断用户意图，再选择流程；不得因为消息同时出现日期、产品名称或“产量/产能”就自动当作生产报数。

- **历史统计/产能分析流程（只读）**：用户出现“统计、汇总、分析、产能、总产量、历史记录、日期范围、按某人/某机器口径”等表达，且没有逐项填写本次生产数量时，进入查询流程。按生产日筛选正式台账，计算总量、记录数、日均/区间产能，并列出计算依据和缺失项。
- **生产报数/补报流程（可核对、可上传）**：只有消息明确表示要报数、补报或更正，并同时包含员工身份、生产日期、工序和六项产品数量（没有生产的项目明确为 0），才进入核对卡流程。
- 统计查询流程严禁生成“生产补报数核对”卡、要求回复“准确”、上传 GitHub、修改台账或等待生产批次确认；只能读取并汇总，缺失数据标记为“缺失”，不得按 0 计算。
- 统计查询涉及跨年日期时，已明确起止年份就直接执行；不要再次询问年份。若区间包含尚未发生的日期，只统计已发生且已有正式记录的部分，并在结果中注明未发生日期范围。
- 用户说“按李鸿玉记录”“按下机机器记录”等是统计口径，不是员工报数身份，也不是补报模板字段。机器编号未在台账中唯一对应时，将该口径列为“缺失/无法匹配”，不得把员工总量擅自分配给机器。
- 群内统计默认只回复汇总结果和缺失项。若消息发送者已识别为老板本人或经核实管理员，允许在生产群直接查询并回复正式台账中的员工月度/区间汇总；仍不在群内展开员工逐日明细，逐日明细继续转到有权限的老板私聊查询。员工查询他人数据时，仍按隐私规则拒绝或引导私聊，不得把查询请求改写成报数流程。

当前纳入的产品：

- 棉堆堆袜
- 冰冰袜
- 小腿袜
- 过膝袜
- 女船袜
- 男船袜

产品名称以以上六项标准名称入账。解析层兼容已确认的常见笔误“冰袜袜”，自动归一为“冰冰袜”；核对卡继续显示标准名称。其他不确定或无法归一的产品名称必须先核实，不得猜测合并。

“魔术袜”暂不纳入，除非另行明确启用。

## V1.15 当前缺失日期核实规则

- 核实卡只保留三个选项：1．当天未上班；2．已经报过；3．需要补报。
- 三种选项都必须在员工确认后同步 GitHub；飞书回复本身不等于同步完成。
- 当天未上班：生成“出勤状态核对”卡，不显示六项 0 双生产清单；员工确认后同步 GitHub 出勤核实状态，保留日期审计记录，但不写入生产明细、生产天数、产量或个人/月度/年度累计。
- 已经报过：生成“已报记录核实”卡，记录已报待查状态；员工确认后不重复增加生产数量，也不生成六项 0 双明细。
- 需要补报：逐日发送模板，员工只填写六个数量，生成“生产补报数核对”卡，回复“准确”后按正常 commit、远程回读和成功回执流程上传，并在回执中标记“记录类型：补报”。
- 自动和手动补报首先使用同一张“补发生产日期待核实”卡，只保留“1 当天未上班、2 已经报过、3 需要补报”三个选择。三种选择都必须生成对应核对批次，员工核对后统一走 GitHub 提交、远程回读和飞书回执链路；只有选择 3 后才发送“补报生产数据”六项填写模板。模板回传必须保留员工、日期、工序和六个产品名称，六项完整后才生成“生产补报数核对”卡。
- 同一员工有多日缺失时，首张卡明确列出待处理日期队列，但每张卡只填写当前生产日期；当前日期 GitHub 提交、远程回读和飞书成功回执全部完成后，自动发送下一日期，不批量混填。只有一天时，完成后停止。
- GitHub 写入、回读或飞书成功回执失败时，当前日期保持待处理，不发送下一日期。
- 台账中的日期标题或“暂无有效记录”占位不算有效生产记录；只有该员工该日期下存在已确认的正式明细行时才拦截重复补报。若旧版本已将占位误判为重复并阻断确认，修复后沿用原确认回执恢复，不要求员工重新确认。

### V1.15 自动与手动补报统一执行口径

- 自动缺失提醒和员工手动补报使用同一套日期队列、核对卡、确认回执、GitHub 写入、远程回读和飞书成功回执状态；两条入口不得各自维护一套上传逻辑。
- 选项“当天未上班”和“已经报过”也必须生成状态专用核对批次，员工回复“准确”后走同一 GitHub 提交、远程回读和成功回执流程；前者写入“已确认未上班”，后者写入“已报待查”，两者都不写入生产明细或累计。只有选项3生成六项“生产补报数核对”卡并按数量上传。
- 手动选择“当天未上班/已经报过”生成的状态批次必须写入与自动入口相同的主收件库，并绑定已核实员工身份；不得写入补报专用临时库。状态批次来源必须保持可校验的 `om_` 消息格式，核对卡、确认回执、GitHub 上传和远程回读必须使用同一来源 ID。
- 老板可代员工点击状态按钮进行测试或纠正，但生成的核对卡必须绑定目标员工已核实账号；员工本人后续回复“准确”后才能上传，其他未绑定账号不得代替员工确认。
- 状态批次的来源 ID 按目标员工账号和生产日期生成，不能按点击按钮的账号生成；旧测试来源不得复用或阻塞新的核对卡。
- 月度汇总固定保留 A/B/C/D 员工行；无有效生产时使用“—”和“0日”，状态说明放在覆盖表和状态区，避免员工因无生产记录从月表消失。
- 服务每5分钟以内轮询一次待核实状态，状态不变时不改写快照、不调用模型；重启后从 SQLite 和本地状态快照恢复，员工无需反复提醒管理员刷新。
- 核实卡撤回后重新发送必须使用新的平台幂等 ID；不得复用已撤回消息的发送 ID。
- 自动提醒发送后会检查飞书卡片是否已被撤回；明确撤销的原批次停用，禁止恢复扫描自动重发。经明确授权重新建立有效任务时使用新的平台幂等 ID；普通网络重试复用当前幂等 ID。
- 只有当前日期的 GitHub 提交、远程回读和飞书成功回执全部完成，才解除同一员工下一日期的队列锁。成功回执缺失时，当前日期保持“回执待补”，不得提前发送下一张卡。
- 每个生产日只发送一张补报卡；服务重启、网络恢复或重复扫描只恢复原批次，不创建重复卡。自动入口已经存在的日期，手动入口不得再发送第二张同日卡。
- 缺失提醒按生产日的下一个自然日中午 12:00 执行，周六、周日和节假日照常执行；这里的“工作日”不跳过周末，含义是进入下一次日间处理窗口。

## 身份与同步边界

- 员工可以用 A、B、C、D 代号报数，也可以先用姓名报数；姓名只能原样保留，不能仅凭模糊姓名猜测身份。
- 对已经由老板或经核实管理员确认过的账号映射，系统可以自动识别员工身份；当前身份映射为：A=徐超超、B=梅芳、C=李鸿玉、D=张小翠。
- 每次核对时必须把自动识别结果明确显示为“身份：A=徐超超，请核实”“身份：B=梅芳，请核实”“身份：C=李鸿玉，请核实”或“身份：D=张小翠，请核实”，让员工和老板同时核对身份与数量。
- 如果账号没有可靠映射，不能自动猜测或强行归入 A、B、C、D；应显示身份待核实，并按现有身份确认流程处理。
- 身份映射变更必须由老板或经核实的管理员明确确认，并留下确认依据。
- 老板私聊只同步明确涉及“袜子生产统计工作台”的报数、纠正、撤销、核对、规则确认和统计查询；普通聊天、其他项目内容和示例文字不进入工作台。
- 老板私聊与实际生产群共用同一套待核对状态，但同步不是补录：不得重放历史消息或把规则示例当作生产记录。
- 群内公开回复不得向普通员工泄露他人逐日明细；老板本人或经核实管理员在生产群查询时，可以查看全部已上传员工的汇总结果。老板私聊可以查看全部已上传员工数据，普通员工只能查看本人。

## 数据状态与来源

每条消息按以下状态流转：`收到待解析` → `待核对` → `已确认待上传` → `已上传`，或标记为`已拒绝/已撤销/解析失败`。只有 GitHub 写入和推送均取得成功回执，才能称为“已上传”。

每条明细必须保存：原始消息 ID、来源会话（群或老板私聊）、报数员工原文身份、确认身份、生产日、员工实际报数时间（精确到分钟）、工人代号（如已核实）、班次、产品、工序、数量、状态和更正关联。

## 固定流程

每个员工的每个批次按以下顺序执行；不同员工可以并行，不等待其他员工确认或上传：

1. 收到员工报数。
2. 按**生产日**建立独立批次；每天单独记账，不把前一天数量叠加到当天。
3. 按产品和工序整理报数；产品显示固定序号：1 棉堆堆袜、2 冰冰袜、3 小腿袜、4 过膝袜、5 女船袜、6 男船袜。
4. 产品名称不同必须分别保留，不因名称相近、序号或数量相近而合并。
5. 列出本次各产品数量和当天合计，单位统一为“ 双”。
6. 对六个产品逐项核对：员工明确填写 0，或完全没有收到数量的产品，核对卡统一显示为“0双（数量为0，请核实）”。员工回复“准确”后，未上报项目按 0 双入账；若实际忘记上报，回复“**错误**”并重报完整、正确的六项生产数量，系统重新生成完整核对卡。
7. 每条记录必须保留两类时间：生产日和员工实际报数时间（年、月、日、时、分）。生产日有明确日期时按原文；未提供日期时按消息时间自动补入上海时区生产日，以 07:00 为切日，并保留“自动补入”标记；员工说“补昨天/补前天”时优先按该说明。
8. 每名员工独立核对和统计：A 只处理 A 的报数，B 只处理 B 的报数，C 只处理 C 的报数，D 只处理 D 的报数。可靠账号映射可以自动识别身份，但核对清单仍必须显示“字母=姓名，请核实”。班次和员工代号是可选信息，缺失时留空或标记“未提供”，不追问、不阻止数量核对。
9. 不要求员工分多次回答。系统应在一条核对消息中同时列出身份、六个产品、已报合计和处理说明；员工只需核对完整清单后回复“准确”。
10. 对未上报产品，不要求员工先单独回复身份或逐项说明未上机；核对无误回复“**准确**”即可。若实际漏报或数量有错，回复“**错误**”并重报完整、正确的六项生产数量，缺项明确填写0；系统按新报数重新生成完整核对卡。
11. 员工发现数量或身份错误时，回复“**错误**”，并直接重报完整、正确的六项生产数量，缺项明确填写0；身份有误时同时说明正确身份。系统不得把错误批次上传，必须按新报数重新生成完整核对卡。
12. 只有身份和六个产品的当前完整清单均无误，并由有权确认的人明确回复“准确”后，才进入已确认待上传状态；系统必须把这条“准确”关联到当前原报数消息 ID，不能把其他批次或普通聊天中的“准确”当作确认。
13. GitHub 文件写入、提交和推送全部成功后，才能报告实际上传成功；任一步失败都必须报告未上传及失败原因。

员工不需要回复“C确认”、完整姓名或多种复杂口令。正常情况下只需回复一次“**准确**”；有错回复“**错误**”并重报完整、正确的六项生产数量，缺项明确填写0。

## 网络恢复后的补处理与防重复发送（2026-09-23）

- 只有原始报数已成功持久化，并保存唯一的原始消息 ID、发送人、来源会话、原文和接收时间，才视为‘已接收’，才允许进入恢复补处理。
- 恢复扫描只处理已接收且尚无有效核对卡片的真实报数；模板、规则说明、重复提示、更正回复和普通聊天不触发数量核对。
- 同一原始消息 ID 最多生成一张有效核对卡；已有核对卡、确认记录、上传记录或明确跳过记录时，不重复建批次、不重复发送。
- 核对卡发送成功必须保存飞书发送回执，并与原始消息 ID 绑定；‘已接收’不等于‘已发核对卡’，‘已发核对卡’不等于‘已确认’或‘已上传’。
- 网络恢复补卡只进入待核对状态，明确标记‘网络恢复后补处理’，不自动确认、不自动写入、不自动提交或推送 GitHub。员工本人（或有权确认人）核对当前完整清单后回复‘准确’，才可进入既有上传防护。
- 网络恢复、服务重启或重复扫描不得产生第二张卡片；发送回执不明确时保持待核实，禁止盲目重发。

## 核对卡发送失败与未查看补发（2026-09-25）

- 核对卡发送失败或发送回执明确失败时，生产服务每 30 秒扫描待处理记录；仅在既有发送重试条件满足时重试，扫描不代表无限上传重试。发送成功前不能把卡片标记为“已发送”。
- 飞书接口返回发送成功，只能证明平台接受了消息，不能证明员工已经看到或完成核对。卡片保持“待核对”，直到收到与当前原始报数消息绑定的有效确认。
- 卡片已发送但员工尚未确认时，首次发送后 5 分钟自动补发一次；第一次补发后再等待 30 分钟，最多补发第二次。
- 员工确认后立即停止后续补发；补发不改变原始报数、员工归属、生产日或数量，也不创建新的生产批次。
- 每次发送和补发都保存平台消息 ID、发送时间、补发次数和失败原因；同一核对卡最多补发两次，避免无限刷屏。
- 核对卡有效期为 24 小时。过期、拒绝、撤销或已上传的卡片不再补发。
- 补发仍只发送到原核对卡绑定的群会话，不得因为重试把卡片发给其他员工或串用其他批次。

## 员工确认回执异常恢复（2026-09-25）

- 员工发送“准确”“确认”或“确认上传”后，系统先把确认消息 ID、发送人、群会话和对应核对卡保存为持久化确认回执，再启动 GitHub 上传。
- 确认绑定或上传任务因网络、服务或运行时异常未启动成功时，回执保持待处理；OpenClaw 每 30 秒扫描恢复队列，仅对符合重试条件的同一员工、同一来源和确认消息恢复任务。同一确认自动上传尝试累计最多3次，达到上限后停止自动上传并转管理员处理；修复后可使用原报数和原确认恢复该批次，员工不必重新报数或重新确认。
- 同一确认消息 ID 幂等处理；员工重复发送“准确”时返回当前同一批次的已处理或处理中状态，不重置尝试上限、不创建新批次、不重复写入台账，也不使用其他员工的来源或数量。
- 确认回执已绑定但 GitHub 写入失败时，保存真实错误原因；例如台账缺少月份区块时，员工状态显示“已确认，上传因台账月份结构失败”，不误提示重新报数或重新确认。该批次仍未上传，可按上述上限重试或在管理员修复后恢复；只有真实 commit 和远程回读一致后才能发送成功回执。
- GitHub 已验证但飞书成功回执失败时，仅补发该批次的成功回执，最多自动重试3次；连续失败转人工补发，不再次写入 GitHub，也不重复计量。
- 如果消息在员工设备或网络侧完全没有到达飞书，系统没有可恢复的消息凭证；网络恢复后员工需重新发送一次“准确”。

## 禁止事项

- 确认前不得写入正式 GitHub 台账。
- 确认前不得说“已记录”“已上报”或“已上传”；只能说“待核对、尚未上传”。
- 未收到与当前完整核对卡绑定的有效确认，不得放行上传；员工回复“准确”后，卡片中已明确展示的核实项按0双入账，不再要求逐项确认。
- “收到”“看到了”“好的”“准确”“没问题”等不带当前批次上下文的聊天回复，不得视为确认。
- 不得把本地测试状态、模拟消息或测试数量写入正式台账。
- 不得把员工补报、纠正或未上机说明遗漏。
- 核对卡不得把待核实项目隐藏；待核实项目统一显示“0双（数量为0，请核实）”。未上报只有在员工补报前保持待核实，员工回复“准确”后才按 0 双写入。

## 报数口径

- A、B：下机工，记录“下机”数量。
- C=李鸿玉、D=张小翠：烤边工，记录“烤边”数量；“烤头”是历史称呼，收到后统一规范化为“烤边”，不再建立独立的“烤头”统计列。C、D均按白天为主、可能加班/时间不固定处理，不参与 A/B 半月换班。
- 数量单位为双。
- 每名员工、每条原始报数单独保留；同一消息重复到达时按原始消息 ID 去重，不重复入账。
- 更正和撤销追加记录并关联原消息；不删除原始记录。最终汇总只计算有效记录。
- A、B、C、D 的报数和统计相互隔离；当天核对只针对当天，不把前一天数量累加到当天。
- 老板可确认全部员工批次；员工只能确认和查询本人批次。身份未核实时只返回待核实，不返回他人明细。
- 月度、年度和日期区间统计必须先按生产日筛选已上传的正式明细，再重新汇总。

- 无人点名的适宜聊天轮流接话，主动接话有60秒冷却；同一发送人10分钟内的普通跟进尽量由原搭档接续。明确回复其他员工或点名其他员工时不抢答。机器人消息不触发互聊。
- 幽默不得针对员工工资、产量高低、失误、外貌或隐私。闲聊、夸张、示例不是生产记录；小文收到含生产关键词的闲聊也须判断原意，不可直接写入。
- 上传确认改为当前完整清单后的“准确”。普通“准确、好的、没问题”等脱离当前批次上下文的聊天不能作为上传确认；系统必须关联原报数消息 ID。期间有补充或更正时继续待核对，不绕过写入防护。
- 元旦、春节、清明、劳动节、端午、中秋、国庆当天，由小文代表两位搭档统一祝福一次。本机任务在北京时间09:00—17:00每小时检查，脚本允许当天09:00—18:00补发；持久去重，失败或回执不明确需核实，不盲目重发。本机与任务运行时段都必须可用。
- 本次通过消息分流、批次确认、节日日期和去重的隔离测试；没有生成测试生产记录或发送群测试消息。真实群端到端聊天送达仍待下一次正常消息验证。


## 网络恢复后的未闭环补处理与防重复发送（2026-09-23）

当网络、模型或服务异常恢复后，小文只扫描已持久化接收、保留原始消息 ID、来源会话、发送人、时间和原文的员工原始报数；模板、规则说明、补充提示、确认/更正回复或仍在解析/解析失败的消息不得直接触发新批次。

补处理前必须按“来源会话 + 原始消息 ID”查询批次和核对卡记录：已有有效核对卡、卡片发送回执、确认、拒绝/撤销或 GitHub 上传记录的，直接跳过；同一原始消息 ID 最多生成一张有效核对卡。网络恢复、服务重启或重复扫描不得重复建批次、重复发卡或重复上传。

只有原始报数已成功解析且该消息 ID 尚无有效核对卡时，才可生成一张标记“网络恢复后补处理”的待核对卡。发送结果未知时，先查询发送回执/幂等记录，不得盲目重发；只有保存平台卡片 ID 和发送回执后，状态才可显示为“核对卡已发送”。

状态必须分开显示：“原始报数已接收”不等于“核对卡已发送”，“核对卡已发送”不等于“员工已确认”，也不等于“已上传”。补卡仅进入待核对；仍须当前批次有权确认人回复“准确”，之后才允许按正常 GitHub 版本检查、写入、提交、推送和远程回读流程处理。


## 统一成功上传回执（2026-09-23）

所有员工（A、B、C、D）的成功上传回执统一使用蓝色标题、白色正文的飞书 interactive 卡片，保留详细凭证内容。员工字段按已核实映射同时显示代号与姓名，例如“员工：B（梅芳）”；随后列出生产日、工序，再逐项列出棉堆堆袜、冰冰袜、小腿袜、过膝袜、女船袜、男船袜六项数量和合计。

回执最后必须连续列出三项提交凭证：

- 原始报数消息 ID
- 确认消息 ID
- GitHub commit

随后明确写出“已回读 GitHub 核实”及核实结论。远程回读一致后，回执必须追加以下区块，其中文件名和 commit 均取自本次实际上传结果：

```text
GitHub 回执
已更新：<本次实际上传的对应年份台账文件名>
同步验收：全部一致
生产统计工作台版本：<运行时 VERSION.json 中的实际版本>
远程 commit：<本次真实 commit>
```

只有 GitHub 写入、提交、推送和远程回读全部取得真实回执，才允许使用“已确认并上传成功”和上述 GitHub 回执。版本号只在这段成功 GitHub 回执中展示，核对卡继续不展示版本号或内部 ID。缺少任一凭证时，只能报告“已确认但尚未上传”或“上传失败”，不得套用成功模板。六项明细必须保留 0 双（含核实后按 0 入账）的说明，不得用合计替代产品明细或只报告远程提交回执。

## V1.1 可靠性补充（2026-09-28）

- 确认入口必须先绑定当前员工、当前群和当前来源消息；确认消息先写入持久化回执，再启动上传。
- 同一来源只允许一个最早有效确认进入上传；后续重复“准确”只返回已处理/处理中，不创建新卡、不重复上传、不重复计量。
- GitHub 已验证但飞书成功回执尚未确认时，状态为“回执待补”，禁止再次提交；仅自动重试成功回执，最多3次，连续失败转人工补发。补发成功回执后才转为完成。
- 运行时以 OpenClaw 实际加载的 `scripts/production-parallel/VERSION.json` 和扩展入口为准；规则文件、核对卡、运行时版本必须一起升级，普通状态查询不调用模型。
