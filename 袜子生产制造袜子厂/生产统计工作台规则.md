# 袜子生产统计工作台规则

## 适用范围

本规则适用于袜子生产统计工作台的群内报数、老板私聊同步、核对、查询和 GitHub 台账入账。

工作台的唯一正式数据来源是经过核对并上传成功的 GitHub 台账；群聊历史回复、模型记忆、计划数量和测试数据都不是正式数据来源。

当前纳入的产品：

- 棉堆堆袜
- 冰冰袜
- 小腿袜
- 过膝袜
- 女船袜
- 男船袜

“魔术袜”暂不纳入，除非另行明确启用。

## 身份与同步边界

- 员工可以用 A、B、C 代号报数，也可以先用姓名报数；姓名只能原样保留，不能由系统猜测或自动绑定到 A、B、C。
- 只有老板或经核实的管理员明确确认姓名与代号对应后，才允许建立绑定；绑定变更必须留下确认依据。
- 老板私聊只同步明确涉及“袜子生产统计工作台”的报数、纠正、撤销、核对、规则确认和统计查询；普通聊天、其他项目内容和示例文字不进入工作台。
- 老板私聊与实际生产群共用同一套待核对状态，但同步不是补录：不得重放历史消息或把规则示例当作生产记录。
- 群内公开回复不得泄露员工私密查询结果；老板私聊查询可以查看全部已上传员工数据，员工只能查看本人。

## 数据状态与来源

每条消息按以下状态流转：`收到待解析` → `待核对` → `已确认待上传` → `已上传`，或标记为`已拒绝/已撤销/解析失败`。只有 GitHub 写入和推送均取得成功回执，才能称为“已上传”。

每条明细必须保存：原始消息 ID、来源会话（群或老板私聊）、报数员工原文身份、确认身份、生产日、员工实际报数时间（精确到分钟）、工人代号（如已核实）、班次、产品、工序、数量、状态和更正关联。

## 固定流程

每个员工的每个批次按以下顺序执行；不同员工可以并行，不等待其他员工确认或上传：

1. 收到员工报数。
2. 按**生产日**建立独立批次；每天单独记账，不把前一天数量叠加到当天。
3. 按产品和工序整理报数；产品显示固定序号：1 棉堆堆袜、2 冰冰袜、3 小腿袜、4 过膝袜、5 女船袜、6 男船袜。
4. 产品名称不同必须分别保留，不因名称相近、序号或数量相近而合并。
5. 列出本次各产品数量和当天合计，单位统一为“ 双”。
6. 对六个产品逐项核对；没有收到数量反馈的产品必须显示为“核实”，不能自动写成“未上机”或 0 双。
7. 每条记录必须保留两类时间：生产日（按班次归属）和员工实际报数时间（年、月、日、时、分）。
8. 每名员工独立核对和统计：A 只处理 A 的报数，B 只处理 B 的报数，C 只处理 C 的报数；姓名身份未核实前不得强行归入代号。
9. 对每个显示“核实”的产品固定询问：“请确认某某产品是忘记上报数量，还是本次未上报。”
10. 等员工或老板核对；如有补报或更正，更新清单并重新发起核对，不能直接覆盖原始消息。
11. 只有本批次六个产品的缺项全部处理，并由有权确认的人明确回复“确认上传 <原报数消息ID>”后，才进入已确认待上传状态。
12. GitHub 文件写入、提交和推送全部成功后，才能报告实际上传成功；任一步失败都必须报告未上传及失败原因。

## 禁止事项

- 确认前不得写入正式 GitHub 台账。
- 确认前不得说“已记录”“已上报”或“已上传”；只能说“待核对、尚未上传”。
- 未说明遗漏规格的情况下，即使回复明确的批次上传确认，也不得放行上传。
- “收到”“看到了”“好的”“准确”“没问题”等不带批次的聊天回复，不得视为确认。
- 不得把本地测试状态、模拟消息或测试数量写入正式台账。
- 不得把员工补报、纠正或未上机说明遗漏。

## 报数口径

- A、B：下机工，记录“下机”数量。
- C：烤边工，记录“烤边”数量；“烤头”是历史称呼，收到后统一规范化为“烤边”，不再建立独立的“烤头”统计列。
- 数量单位为双。
- 每名员工、每条原始报数单独保留；同一消息重复到达时按原始消息 ID 去重，不重复入账。
- 更正和撤销追加记录并关联原消息；不删除原始记录。最终汇总只计算有效记录。
- A、B、C 的报数和统计相互隔离；当天核对只针对当天，不把前一天数量累加到当天。
- 老板可确认全部员工批次；员工只能确认和查询本人批次。身份未核实时只返回待核实，不返回他人明细。
- 月度、年度和日期区间统计必须先按生产日筛选已上传的正式明细，再重新汇总。

## 核对示例

收到：

```text
A 冰冰袜 下机 1000 双
A 小腿袜 下机 500 双
```

应先回复：

```text
冰冰袜：1000 双
小腿袜：500 双
合计：1500 双
暂未上报：棉堆堆袜、过膝袜、女船袜、男船袜。请分别说明是“忘记上报”还是“本次未上机”。
以上尚未上传 GitHub，请核对后完整回复“确认上传 <本批次原报数消息ID>”；如有错误，请直接发送更正后的规格和数量。
```

只有在遗漏规格已明确处理，并收到对应本批次的“确认上传 <原报数消息ID>”后，才能上传。正式台账明细中的“上报日期时间”记录员工实际报数时间，不使用确认上传时间。

## 数据清理与版本管理

- 验收或模拟测试产生的临时状态、测试分支、测试数量和模拟消息必须在测试结束后清理。
- 正式 `main` 台账只允许写入已确认的真实生产记录；规则优化、代码验证和示例文本不得生成正式明细。
- 每次规则变更必须同步更新本规则文件、正式台账说明和工作台程序的对应口径，并在更新记录中注明日期与结果。
- GitHub 推送后以远程分支实际提交为准；本地修改、提交成功或发送请求不等于远程上传成功。

## 库存历史表格核验（2026-09-20）

- 库存主账的“更新记录”按日期、更新内容、结果三列连续追加；表格行之间禁止空行，不得把新记录写成表格外的普通文字。
- 提交前及上传后读回时，都要检查从表头到最后一条记录连续无断行；单元格内换行改为空格，原文竖线转义为 `\|`。只有数量核对和表格结构核验都通过，才能报告处理完成。
- 本次修正规范及蓝绿色 +2,945 双记录的断表排版；该笔已入账，格式修复不增加或减少任何库存。

## 小文与元宝并行协作（2026-09-21）

- 原OpenClaw小文CEO负责群内核对和最终入账；本机Hermes元宝以独立、无工具的处理任务整理草稿，不直接改台账。
- 生产群按发送人分开会话；群消息到达先保存共享SQLite收件箱，再交元宝后台预处理，接收入口不等待模型或GitHub上传。
- 元宝最多并行整理两个任务；同一发送人的任务依接收顺序领取。每个来源消息ID唯一；重复消息不重复领取，同ID内容变化保留原始内容并要求明确更正。
- 小文可以并行核对不同员工的批次；元宝未完成或失败时，小文按原始消息自行核对，不等另一人的上传结束。
- 收件成功只表示本地收到，元宝的ready只表示草稿完成；都不代表人工确认或正式上传。
- 上传使用统一写入防护：本人或老板明确确认、关联原消息、本地写锁、远程版本检查、提交后回读。冲突重读合并，不用旧全文覆盖新数据；复杂或不明确的确认保留待核对，不能绕过防护。
- 旧production-sync自动入账入口停用；旧待核对数据保留，不重放历史消息。不得将测试报数写入正式主账。
- 本机启用情况以运行日志为准，仓库说明不等于机器人运行回执。当前已做隔离并发和上传防护测试，尚未以真实员工的新报数完成群到台账全链路验收。


## 员工群双人搭档（2026-09-22）

- 本群同时用于生产与日常聊天。小文负责核对和上传，元宝可自然聊天、讲笑话、关心员工。两边共享同一条消息的主答者决定，普通聊天一次只由一个机器人回答；直接点名优先，两个都被点名则选一个主答。
- 生产相关消息统一交给小文核对，元宝继续在后台并行提取草稿。不限A、B、C中的某两个人。报数和修改保持本人顺序，最终写入仍使用版本检查和写锁。
- 无人点名的适宜聊天轮流接话，主动接话有60秒冷却；同一发送人10分钟内的普通跟进尽量由原搭档接续。明确回复其他员工或点名其他员工时不抢答。机器人消息不触发互聊。
- 幽默不得针对员工工资、产量高低、失误、外貌或隐私。闲聊、夸张、示例不是生产记录；小文收到含生产关键词的闲聊也须判断原意，不可直接写入。
- 上传确认改为完整的“确认上传 <原报数消息ID>”。普通“准确、好的、没问题”等不能作为上传确认。期间有补充或更正时继续待核对，不绕过写入防护。
- 元旦、春节、清明、劳动节、端午、中秋、国庆当天上午，由小文代表两位搭档统一祝福一次。日历任务由本机Codex每日09:00检查；脚本只在09:00—12:00发送，持久去重，失败或回执不明确需核实，不盲目重发。本机与Codex需运行。
- 本次通过消息分流、批次确认、节日日期和去重的隔离测试；没有生成测试生产记录或发送群测试消息。真实群端到端聊天送达仍待下一次正常消息验证。
