# 袜子生产统计工作台规则

## 适用范围

本规则适用于袜子生产统计工作台的群内报数、老板私聊同步、核对、查询和 GitHub 台账入账。

工作台的唯一正式数据来源是经过核对并上传成功的 GitHub 台账；群聊历史回复、模型记忆、计划数量和测试数据都不是正式数据来源。

当前纳入的产品：

- 棉堆堆袜
- 冰冰袜
- 小腿袜
- 过膝袜
- 女船袜
- 男船袜

“魔术袜”暂不纳入，除非另行明确启用。

## 身份与同步边界

- 员工可以用 A、B、C 代号报数，也可以先用姓名报数；姓名只能原样保留，不能仅凭模糊姓名猜测身份。
- 对已经由老板或经核实管理员确认过的账号映射，系统可以自动识别员工身份；当前身份映射为：A=徐超超、B=梅芳、C=李鸿玉。
- 每次核对时必须把自动识别结果明确显示为“身份：A=徐超超，请核实”“身份：B=梅芳，请核实”或“身份：C=李鸿玉，请核实”，让员工和老板同时核对身份与数量。
- 如果账号没有可靠映射，不能自动猜测或强行归入 A、B、C；应显示身份待核实，并按现有身份确认流程处理。
- 身份映射变更必须由老板或经核实的管理员明确确认，并留下确认依据。
- 老板私聊只同步明确涉及“袜子生产统计工作台”的报数、纠正、撤销、核对、规则确认和统计查询；普通聊天、其他项目内容和示例文字不进入工作台。
- 老板私聊与实际生产群共用同一套待核对状态，但同步不是补录：不得重放历史消息或把规则示例当作生产记录。
- 群内公开回复不得泄露员工私密查询结果；老板私聊查询可以查看全部已上传员工数据，员工只能查看本人。

## 数据状态与来源

每条消息按以下状态流转：`收到待解析` → `待核对` → `已确认待上传` → `已上传`，或标记为`已拒绝/已撤销/解析失败`。只有 GitHub 写入和推送均取得成功回执，才能称为“已上传”。

每条明细必须保存：原始消息 ID、来源会话（群或老板私聊）、报数员工原文身份、确认身份、生产日、员工实际报数时间（精确到分钟）、工人代号（如已核实）、班次、产品、工序、数量、状态和更正关联。

## 固定流程

每个员工的每个批次按以下顺序执行；不同员工可以并行，不等待其他员工确认或上传：

1. 收到员工报数。
2. 按**生产日**建立独立批次；每天单独记账，不把前一天数量叠加到当天。
3. 按产品和工序整理报数；产品显示固定序号：1 棉堆堆袜、2 冰冰袜、3 小腿袜、4 过膝袜、5 女船袜、6 男船袜。
4. 产品名称不同必须分别保留，不因名称相近、序号或数量相近而合并。
5. 列出本次各产品数量和当天合计，单位统一为“ 双”。
6. 对六个产品逐项核对：员工明确填写 0 的产品显示为“0双，请核实”；完全没有收到数量的产品显示为“未上报”，不得自动写成 0 双。
7. 每条记录必须保留两类时间：生产日和员工实际报数时间（年、月、日、时、分）。生产日有明确日期时按原文；未提供日期时按消息时间自动补入上海时区生产日，以 07:00 为切日，并保留“自动补入”标记；员工说“补昨天/补前天”时优先按该说明。
8. 每名员工独立核对和统计：A 只处理 A 的报数，B 只处理 B 的报数，C 只处理 C 的报数。可靠账号映射可以自动识别身份，但核对清单仍必须显示“字母=姓名，请核实”。班次和员工代号是可选信息，缺失时留空或标记“未提供”，不追问、不阻止数量核对。
9. 不要求员工分多次回答。系统应在一条核对消息中同时列出身份、六个产品、已报合计和处理说明；员工只需核对完整清单后回复“准确”。
10. 对未上报产品，不要求员工先单独回复身份；员工可在核对后直接补发正确数量，或明确说明“某产品未上机”。补报、更正或未上机说明到达后，更新当前清单并重新发起一次完整核对。
11. 员工发现数量或身份错误时，直接重新发送正确的身份或数量；系统不得把错误批次上传，必须用最新完整清单重新核对。也可以回复“错误”，系统随后要求重新发送正确内容。
12. 只有身份和六个产品的当前完整清单均无误，并由有权确认的人明确回复“准确”后，才进入已确认待上传状态；系统必须把这条“准确”关联到当前原报数消息 ID，不能把其他批次或普通聊天中的“准确”当作确认。
13. GitHub 文件写入、提交和推送全部成功后，才能报告实际上传成功；任一步失败都必须报告未上传及失败原因。

- 只有原始报数已成功持久化，并保存唯一的原始消息 ID、发送人、来源会话、原文和接收时间，才视为‘已接收’，才允许进入恢复补处理。

- 同一原始消息 ID 最多生成一张有效核对卡；已有核对卡、确认记录、上传记录或明确跳过记录时，不重复建批次、不重复发送。
- 核对卡发送成功必须保存飞书发送回执，并与原始消息 ID 绑定；‘已接收’不等于‘已发核对卡’，‘已发核对卡’不等于‘已确认’或‘已上传’。
- 网络恢复补卡只进入待核对状态，明确标记‘网络恢复后补处理’，不自动确认、不自动写入、不自动提交或推送 GitHub。员工本人（或有权确认人）核对当前完整清单后回复‘准确’，才可进入既有上传防护。
- 网络恢复、服务重启或重复扫描不得产生第二张卡片；发送回执不明确时保持待核实，禁止盲目重发。
需回复一次“准确”；发现问题时直接重发正确身份或数量，系统整理后再次发出完整核对清单。

## 禁止事项

- 确认前不得写入正式 GitHub 台账。
- 确认前不得说“已记录”“已上报”或“已上传”；只能说“待核对、尚未上传”。
- 未说明遗漏规格的情况下，即使回复明确的批次上传确认，也不得放行上传。
- “收到”“看到了”“好的”“准确”“没问题”等不带当前批次上下文的聊天回复，不得视为确认。
- 不得把本地测试状态、模拟消息或测试数量写入正式台账。
- 不得把员工补报、纠正或未上机说明遗漏。
- 不得把未上报自动改写成 0，也不得把明确的 0 改写成未上报。

## 报数口径

- A、B：下机工，记录“下机”数量。
- C：烤边工，记录“烤边”数量；“烤头”是历史称呼，收到后统一规范化为“烤边”，不再建立独立的“烤头”统计列。
- 数量单位为双。
- 每名员工、每条原始报数单独保留；同一消息重复到达时按原始消息 ID 去重，不重复入账。
- 更正和撤销追加记录并关联原消息；不删除原始记录。最终汇总只计算有效记录。
- A、B、C 的报数和统计相互隔离；当天核对只针对当天，不把前一天数量累加到当天。
- 老板可确认全部员工批次；员工只能确认和查询本人批次。身份未核实时只返回待核实，不返回他人明细。
- 月度、年度和日期区间统计必须先按生产日筛选已上传的正式明细，再重新汇总。

## 生产日期与可选字段（2026-09-22）

- 生产日期优先采用员工消息中明确写出的日期；没有明确日期时，程序按消息时间自动补入上海时区生产日（07:00 切日），并标记为自动补入，不再要求员工补写日期。
- 班次和员工代号用于补充信息，属于可选字段；没有提供时留空或标记“未提供”，不阻止数量核对、生成清单或后续确认。

## 数据清理与版本管理

- 验收或模拟测试产生的临时状态、测试分支、测试数量和模拟消息必须在测试结束后清理。
- 正式 `main` 台账只允许写入已确认的真实生产记录；规则优化、代码验证和示例文本不得生成正式明细。
- 每次规则变更必须同步更新本规则文件、正式台账说明和工作台程序的对应口径，并在更新记录中注明日期与结果。
- GitHub 推送后以远程分支实际提交为准；本地修改、提交成功或发送请求不等于远程上传成功。

## 库存历史表格核验（2026-09-20）

- 库存主账的“更新记录”按日期、更新内容、结果三列连续追加；表格行之间禁止空行，不得把新记录写成表格外的普通文字。
- 提交前及上传后读回时，都要检查从表头到最后一条记录连续无断行；单元格内换行改为空格，原文竖线转义为 `\|`。只有数量核对和表格结构核验都通过，才能报告处理完成。
- 本次修正规范及蓝绿色 +2,945 双记录的断表排版；该笔已入账，格式修复不增加或减少任何库存。

## 小文与元宝并行协作（2026-09-21）

- 原OpenClaw小文CEO负责群内核对和最终入账；本机Hermes元宝以独立、无工具的处理任务整理草稿，不直接改台账。
- 生产群按发送人分开会话；群消息到达先保存共享SQLite收件箱，再交元宝后台预处理，接收入口不等待模型或GitHub上传。
- 元宝最多并行整理两个任务；同一发送人的任务依接收顺序领取。每个来源消息ID唯一；重复消息不重复领取，同ID内容变化保留原始内容并要求明确更正。
- 小文可以并行核对不同员工的批次；元宝未完成或失败时，小文按原始消息自行核对，不等另一人的上传结束。
- 收件成功只表示本地收到，元宝的ready只表示草稿完成；都不代表人工确认或正式上传。
- 上传使用统一写入防护：本人或老板明确确认、关联原消息、本地写锁、远程版本检查、提交后回读。冲突重读合并，不用旧全文覆盖新数据；复杂或不明确的确认保留待核对，不能绕过防护。
- 旧production-sync自动入账入口停用；旧待核对数据保留，不重放历史消息。不得将测试报数写入正式主账。
- 本机启用情况以运行日志为准，仓库说明不等于机器人运行回执。当前已做隔离并发和上传防护测试，尚未以真实员工的新报数完成群到台账全链路验收。

## 员工群双人搭档（2026-09-22）

- 本群同时用于生产与日常聊天。小文负责核对和上传，元宝可自然聊天、讲笑话、关心员工。两边共享同一条消息的主答者决定，普通聊天一次只由一个机器人回答；直接点名优先，两个都被点名则选一个主答。
- 生产相关消息统一交给小文核对，元宝继续在后台并行提取草稿。不限A、B、C中的某两个人。报数和修改保持本人顺序，最终写入仍使用版本检查和写锁。
- 无人点名的适宜聊天轮流接话，主动接话有60秒冷却；同一发送人10分钟内的普通跟进尽量由原搭档接续。明确回复其他员工或点名其他员工时不抢答。机器人消息不触发互聊。
- 幽默不得针对员工工资、产量高低、失误、外貌或隐私。闲聊、夸张、示例不是生产记录；小文收到含生产关键词的闲聊也须判断原意，不可直接写入。
- 上传确认改为当前完整清单后的“准确”。普通“准确、好的、没问题”等脱离当前批次上下文的聊天不能作为上传确认；系统必须关联原报数消息 ID。期间有补充或更正时继续待核对，不绕过写入防护。
- 元旦、春节、清明、劳动节、端午、中秋、国庆当天，由小文代表两位搭档统一祝福一次。本机任务在北京时间09:00—17:00每小时检查，脚本允许当天09:00—18:00补发；持久去重，失败或回执不明确需核实，不盲目重发。本机与任务运行时段都必须可用。
- 本次通过消息分流、批次确认、节日日期和去重的隔离测试；没有生成测试生产记录或发送群测试消息。真实群端到端聊天送达仍待下一次正常消息验证。


## 网络恢复后的未闭环补处理与防重复发送（2026-09-23）

当网络、模型或服务异常恢复后，小文只扫描已持久化接收、保留原始消息 ID、来源会话、发送人、时间和原文的员工原始报数；模板、规则说明、补充提示、确认/更正回复或仍在解析/解析失败的消息不得直接触发新批次。

补处理前必须按“来源会话 + 原始消息 ID”查询批次和核对卡记录：已有有效核对卡、卡片发送回执、确认、拒绝/撤销或 GitHub 上传记录的，直接跳过；同一原始消息 ID 最多生成一张有效核对卡。网络恢复、服务重启或重复扫描不得重复建批次、重复发卡或重复上传。

只有原始报数已成功解析且该消息 ID 尚无有效核对卡时，才可生成一张标记“网络恢复后补处理”的待核对卡。发送结果未知时，先查询发送回执/幂等记录，不得盲目重发；只有保存平台卡片 ID 和发送回执后，状态才可显示为“核对卡已发送”。

状态必须分开显示：“原始报数已接收”不等于“核对卡已发送”，“核对卡已发送”不等于“员工已确认”，也不等于“已上传”。补卡仅进入待核对；仍须当前批次有权确认人回复“准确/确认/正确”，之后才允许按正常 GitHub 版本检查、写入、提交、推送和远程回读流程处理。

所有员工（A、B、C）的成功上传回执必须统一使用详细凭证格式：先列出员工/代号、生产日、工序，再逐项列出棉堆堆袜、冰冰袜、小腿袜、过膝袜、女船袜、男船袜六项数量和合计。

回执最后必须连续列出三项提交凭证：

- 原始报数消息 ID
